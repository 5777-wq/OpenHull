摘要 / Executive Summary

OpenHull 是一个开源（MIT）的参数化船舶初步设计工具链。输入一份 YAML 设计任务书——船型、载重吨、服务航速、航区、设计吃水——流水线产出 主尺度方案、静水力表、型线型值表与分层 DXF 矢量数据。整条链路可由 AI 智能体编排，也可以被工程师当作普通 Python 库调用。

本项目的核心主张不在于算法本身——所用的经验公式（Watson、Lackenby、 Holtrop–Mennen、ICLL 干舷规则）全部来自公开教材与国际规范，没有一条是自创的。 主张在于工程化的可信度：每一条公式必须先进入"公式白名单"才能被实现， 并附上书名、章节与公式号；每一次验收只认公开基准船的出版数字； 每一处近似与循环论证都写在明处，而不是藏进精度表里。

首个公开版本 v0.2 交付三段链路——任务书驱动的重量浮力平衡、主尺度初估、 静水力与初稳性，以及参数化型线生成（数字化母型 → 仿射缩放 → Lackenby 变换 → 型值表与分层 DXF）。全部通过日本 NMRI 公开基准船 JBC 的验收锚点： 排水体积误差 +0.21 %（容差 ±1 %）、 KM 误差 +0.000 %（容差 ±2 %）、 方形系数偏差 +0.0018（容差 ±0.005）。 母型船变换链路另以 1963 年 DTMB Report 1712 的印刷棱形系数与解析闭式解， 完成不依赖任何外部拟合数据的非循环验证。

01

问题：初步设计中的三重断裂

船舶设计的信息化程度并不低——CAD、CFD、船级社计算软件一应俱全。 但这些工具高度集中在详细设计与交付环节。 而在更早的初步设计阶段，即"给定载重吨与航速，这个船长什么样"这一步， 工程实践仍然高度依赖人的经验、Excel 台账和零散的内部脚本。 这里存在三重断裂。

1.1 知识是公开的，工具是闭源的

商业船舶软件真正垄断的是交付链条——出图、送审、生产文件。 而初步设计赖以成立的知识内核：母型船统计回归、系列试验图谱、Lackenby 船型变换、 Holtrop–Mennen 阻力估算，全部公开在教材、学位论文与半个世纪前的试验报告里。 换句话说，被锁住的不是知识，而是知识的工程化载体。

1.2 数据在软件之间靠人手搬运

一个典型的初步设计循环是：从任务书读数 → 在 Excel 里估主尺度 → 手抄进 CAD 建母型 → 导出型值 → 另开一个脚本算静水力 → 把结果抄回 Excel 画曲线。每一次人工搬运都是一次精度损失与一次可追溯性的断裂。 本项目要替代的正是这只"在软件之间搬运数据的手"。

1.3 可追溯性缺失

开源界并不缺船舶计算代码。生态调研显示，静水力、稳性、Holtrop 阻力都有多个实现， 但绝大多数是课程作业级：公式来源不明、适用边界不声明、 验收标准是"和某个软件对上了"而非"和出版数据对上了"。 对一个要用于真实产品设计的工具，这不可接受—— 行家一眼就能看穿一个没有出处的系数。

由此得出的判断

真正的卡点不是"缺少算法"，而是被验证过的工程知识的数字化，以及由此建立的行业信任。 OpenHull 的全部设计决策都服务于这两件事。

02

设计立场：四条原则

这四条原则写进了项目宪法 AGENTS.md，是该仓库中优先级最高的一份文件—— 任何代码、测试或文档与它冲突，以它为准。英文版为准，中文版同步维护。

P1

每一个输出结果都必须可追溯至某条公式或公开文献

公式必须先被列入宪法第五节的白名单才能实现；每个实现旁附引用注释， 写明书名、章节与公式号，且页码必须在实现时对着纸质或 PDF 原文核对—— 禁止凭记忆写页码。

P2

与公开基准船数据的验证，优先于新功能开发

任何一条数值若没有出版来源或经业主批准的锚点，就不允许被测试断言。 估计值永远不能充当验证目标。这意味着功能进度可以慢，验证不能欠账。

P3

经验公式必须声明适用范围，超范围的输入一律拒绝

每个经验公式把它适用的 Froude 数、船型系数区间与尺度区间作为数据 写在实现旁边。超出范围时模块抛错并说明违反了哪条边界， 而不是静默外推。静默外推是开源工程代码最危险的失效模式。

P4

能写成公式的交给自动化，写不成公式的留给工程师

这条边界决定了项目范围。船型变换、静水力积分、规则校核可以自动化； 舱室划分的合理性、总布置的工艺判断、与船东的权衡，不在此列， 也不试图用启发式规则假装解决。

工程上，P3 与 P4 直接塑造了架构：算法以注册表形式暴露。 每个计算步骤（主尺度初估、重量估算、船型变换……）都是一个可以挂多个 具名算法的策略点，每个算法携带稳定的 id、它的白名单引用、 以及适用范围数据。任务书因此可以逐步指定算法，未来的图形前端可以据此 把超出范围的选项置灰。

03

系统架构

架构只有一条硬要求：数值内核与调用方式解耦。 CLI 与 YAML 任务书构成稳定契约，全部计算是「输入经过校验的数据类、 输出可 JSON 序列化的纯函数」。这样 MCP server、Skill 或图形界面 可以在不触碰任何一个数值的前提下包装整套能力。

3.1 任务书即输入契约

唯一的用户输入是一份 YAML 任务书。它不只是参数清单，更是出处登记表： 每一个数字都带来源标签。以仓库中的 TB-001（Capesize 散货船）为例：

  • [NMRI] —— 取自日本 NMRI 官方发布的 JBC 条件表（设计吃水 16.500 m、服务航速 14.5 kn、方形系数 0.8580）
  • [DERIV] —— 由 [NMRI] 值按行内写明的公式导出（如排水量 = 1.025 t/m³ × 178 369.9 m³）
  • [ASSUMED] —— 工程假设，需业主批准并留痕（如载重吨 149 920 t：JBC 是虚拟基准船，NMRI 不公布载重吨）

这个设计的直接后果是：任何一个人拿到仓库，都能区分"这是公开数据"与"这是假设"， 而不必去猜某个数字的出处。载重吨这一处最典型——它由业主批准、 取载重吨系数 0.82 的中点值，任务书里连"曾考虑过 0.86 但未采纳"都写了进去。

3.2 算法作为数据

重量估算模块同时注册了三种算法：载重吨系数法（迭代起点）、 成分立方模数法（默认）、成分指数法。默认算法为 component_cubic，其引用字段直接写进每一次运行的输出： 

"citation": "Xie Yunping et al., section 2.2.2: Eq.(2-13) steel cubic
modulus, Eq.(2-42) outfit area modulus, Table 2-3 component shares of
lightweight; Lin Yan, section 2.1.3 Eqs.(2-11)(2-29)"

这意味着结果本身携带审计路径。更进一步，算法还携带适用域—— 例如散货船载重吨系数的回归式只认 0.5 万至 6 万吨，TB-001 的 14.99 万吨 会被正确地拒绝；这个拒绝行为有专门的测试钉死，防止将来有人"顺手放宽"。

3.3 报错也要讲道理

输入校验的失败消息包含四要素：字段、值、允许范围、以及物理或数学上的原因。 如果给一个方形系数 1.5，返回的不是"值非法"，而是 「排水体积塞不进外接矩形框，因此 Cb ≤ 1」并附定义式。 测试直接断言错误文本中含公式，防止将来退化成一句无信息量的报错。 同时所有错误消息保持纯 ASCII——Windows 的 GBK 控制台不会因此崩溃。

04

技术路径

4.1 重量—浮力平衡迭代

主尺度不是一次算出来的，而是"重量等于浮力"这个方程的不动点。 流水线从载重吨系数法给出迭代起点，再用成分法计算空船重量 （钢料立方模数 + 舾装面积模数 + 机电占比），反复逼近。 判停准则采用《船体结构强度》§3.2.2 式(3-27) 的下限 ——两次迭代之间 |W − B|/W ≤ 0.1 %。

迭代同时输出诺曼系数作为物理诊断：它应当大于 1， 因为它描述的是"增加一吨载重会导致排水量增长多少"（增量还包括为此增加的船体本身）。 TB-001 的实测值为 1.160，量级合理。 超过 30 轮未收敛则拒绝返回——避免用无限迭代掩盖一个本就不自洽的输入。

4.2 型线生成：从母型船变换，而不是从零生成

这是型线生成的技术核心，也是本项目的差异化所在。 船体型线是一个光顺性约束极强的连续曲面，从零生成一条可用的型线 是数学上的硬骨头。项目的选择是只做母型船变换： 以一条已知光顺的真实母型为基础，通过仿射缩放改尺度， 再通过 Lackenby 变换调整棱形系数与浮心纵向位置。这条路径的可控性远高于生成式方法。

完整链路共四步：

  1. 母型数字化。包内携带的是 1963 年 DTMB Report 1712 表 7 的 25 站型值表（Model 4214W-B4，总棱形系数 0.805），逐格对着 300 dpi 渲染页核对过。 附带一条纪律上的收获：报告按棱形系数命名系列母型， 文献里常说的 "Series 60, Cb = 0.80" 指的其实是 Cp = 0.805 的这条母型—— 这个术语陷阱已写进数据源文档。
  2. 仿射缩放。把母型缩放到平衡后的主尺度上。船型系数是仿射不变量， 因此这一步有精确的验收标准：半尺度的船排水量必须恰好是全尺度的 1/8（测试断言 rel 1e-9）。
  3. Lackenby 变换。按二次变换函数 dx = c(1−x)(x+d) 移动站线，前后体分别分配棱形系数增量，平行中体保持不动， 以同时命中目标的 Cb 与 LCB。
  4. 表格层收敛（见下）。这是让一阶方法变得可靠的关键。

还有一个细节值得单独记录：教科书中该变换的公式在直读时不闭合。 项目引入了抛物线闭合检验——用一条解析上完全已知的抛物线型线 反推公式中各系数的取值，结果应当精确等于 2/3、3/8、1/5、3/5。 正是这个检验定位到公式转录的口径问题，从而避免了整条链路建立在错误解读上。 解析闭式自证的价值就在这里：它不需要任何外部数据，就能证伪一个实现。

4.3 静水力内核自实现，不用黑箱积分器

辛普森第一/第二法则与梯形法都在包内手写实现。这不是重复造轮子，而是 可追溯性的要求——积分口径直接决定 Cb、LCB、KM 的取值， 而不同积分实现的插值约定差异会悄悄改变结果。 内核提供三向积分：沿水线的纵向要素积分（水线面积、LCF）、 沿垂向的体积与浮心积分、以及沿吃水的邦戎曲线积分。

积分器本身有独立的验收：

  • 箱形船与抛物线型线对闭式解精确到 1e-9
  • 抛物线型线的 Cb 必须等于解析值 2/3
  • 交叉通量检验：邦戎曲线的纵向积分与静水力模块的垂向积分， 两条完全独立的路径必须给出同一个排水体积（实测相对偏差 1e-4）

第三条尤其重要。一个积分实现即使内部约定写错，也可能在单一方向自洽； 只有两条独立路径互相校对，才能真正排除口径错误。

4.4 数值光顺检查

型值表的微小凹凸在 CAD 里会被放大成难看的鼓包，但肉眼在数值表上发现不了。 模块 fairness 用二阶差分的局部对比度做检测： 把每个点的二阶差分与邻近点的中位数比较，取 MAD 鲁棒的 z 分数， 再叠加一个绝对下限形成双门槛。

绝对下限的标定方式值得一提：拿已知光顺的数字化 Series 60 母型实测其最大曲率对比度 （27 条水线 × 21 站，得 12.2），把报警下限设在它的约两倍 （25），并留出"最大对比度 < 0.7 × 下限"的裕量测试。 这样既有明确的物理依据，又不会在将来微调数据时立刻失效。

除了曲率检测，还有两项几何检查：单瓣单调性（仅对 0.5 吃水以上的水线， 球鼻艏区豁免）、以及平行中体的恒定性与摆动判别。 验收是双向的：真实母型零报警， 而人工种植的单点尖峰、斜率折角、破瓣、平行段凹陷全部被检出。 只做前者会把门槛设得过宽，只做后者会误报连连，两个方向必须同时成立。

05

验证体系

这一章是白皮书的重点，也是 OpenHull 与多数同类开源实现的分水岭。 项目的答案是：不是"相信我们的代码"，而是"给你一套可以独立复核的证据链"。

5.1 锚点分层：不同强度的证据不能混用

验证最难的地方在于自证循环——如果用"自己拟合出来的结果"去验证"自己"， 那只是把假设重述了一遍。因此项目对锚点做了严格分层， 并要求在报告里把不同强度的证据分开陈述。

分层的直接应用例证：静水力表里的 TPC、Aw、 KB、LCF 这几项，NMRI 并没有公布 JBC 的对应值。 项目的处理不是"拿一个估计值凑上"，而是明确写出这几个量 无出版锚，改用定义恒等与交叉通量验证， 并给出可执行的替代方案（在真实型值表链路上补做基准核对）。

口径说明：估算尺度 ≠ JBC 尺度

CLI 端到端跑的是完整估算链路——从载重吨出发估主尺度， 再在估算出来的尺度（Lpp 271.633 m）上积分静水力。 而 JBC 的排水体积锚（178 369.9 m³）对应的是 Lpp 280 m 的船。 两者相差 3 % 的船长，排水体积自然不能直接相比。

因此链路验收（±1 %）是在 JBC 尺度与目标上进行的； 而 CLI 端到端只断言 Cb ≤ ±0.005 与 KM ≤ ±2 %。若把 CLI 输出的 ∇ 直接和 JBC 锚并列，得出的"−2.5 %"是一个尺度差异，不是静水力误差。 把这两件事分开报，是本项目验证纪律的一部分。

5.4 把弱点写在明处：循环性与近似清单

很少有技术文档会主动列出自己的循环论证。本项目的立场是： 隐藏的循环性是缺陷，声明过的循环性只是设计选择的结果。 VALIDATION.md 中专门有一节列出全部九条，择要如下：

06

开源生态位

在动手之前，项目对 GitHub 开源生态做了一轮系统普查（约 30 组关键词与 topic 查询，短名单逐一核对许可证、最近提交、README 与文件树）， 结论对定位很关键。

6.1 空白在哪里

Lackenby 变换：全网无可用实现

关键词检索零命中。唯一声称实现该方法的仓库，翻开源码只有 IGES 导入测试脚本， README 第五步是愿望而非代码。这既是空白，也是本项目选择自研的原因—— 公式源取自教材白名单并做了 300 dpi 视觉核对。

Agent 编排层：没有人做成

静水力、稳性、Holtrop 阻力都有小型开源实现，但绝大多数是课程级： 无出处、无适用边界、验收靠"和某软件对上"。把整套链路做成 可被 AI 直接调用的稳定契约，目前没有直接竞品。

与 ML 生成线互补而非竞争

MIT 实验室的 ShipD（30 000 条参数化船体）与 ShipGen（扩散模型生成船体） 在机器学习生成路线上领先。OpenHull 走工程验证路线， 与它们是对话关系——ShipD 的十吃水几何量恰好可作为静水力引擎的 大规模回归语料。

可依赖的成熟基础件

capytaine（线性势流 BEM，Apache-2.0，Nemoh 后继）是水动力模块的 求解器级依赖候选；vesseljs（NTNU，MIT）可作为静水力的第三方交叉验证锚。

6.2 许可证纪律

项目以 MIT 发布，因此对外部代码采取明确的分级策略：

  • MIT / Apache-2.0 / BSD —— 可依赖、可移植，保留署名
  • GPL / AGPL / 无许可证 —— 一行代码都不复制。 GPL 软件的合法用法仅限于"运行它以产生对照数字"； AGPL 因网络服务传染性，连阅读源码都不建议； 无许可证的仓库若功能清单与本项目重合，只能当作功能对照表
  • 数据集 —— 先核清条款再入库。基准船几何一律用官方源头 （NMRI / DTIC），不用 GitHub 上的二手副本
  • 参考实现 —— 只作交叉验证锚，不作真值。 验收数字只认自己跑出来的结果加白名单文献

08

边界：明确不做的事

范围蔓延是这类项目最常见的死因。项目宪法里有一节专门写"禁区"， 这些不是"暂时没做"，而是刻意的排除：

不做理由
CFD 阻力来自白名单经验公式；OpenFOAM 级别的仿真属 v2.0 之后的议题
从零生成自由曲面 船体只能由母型船型值经 Lackenby 变换产生。从零生成光顺曲面是硬骨头， 在变换路径被充分验证之前不碰
详细设计 不做结构构件尺寸、不做船级社送审流程、不做舾装。 输出明确限定在初步设计级别
出品图纸 几何成果以型值表 + 分层 DXF 矢量数据交付，图纸由 CAD 端生成。 PNG/SVG 渲染仅为开发辅助，不是交付物。（此决策由项目所有者拍板，宪法红线已双语更新）
估计值冒充出版值 出处标签是强制项。没有来源的数字必须显式标为假设

最后一条值得多解释一句，因为它看起来像是能力上的退让，实际上是判断力的体现。 项目一度探索过用 FreeCAD TechDraw 的纯 OCC HLR 投影出图，技术路线已经打通 （93 m 实船三视图 SVG/PDF 实际产出过）。 但结论是：几何数据链是精确可靠且有锚验证的，而图面渲染的精度与美感不是 AI 的强项。 与其交付一批"看起来像图纸"但需要工程师逐项返修的东西， 不如把精确的矢量数据和型值表交出去，让 CAD 端做它擅长的事。

09

适用范围与已知边界

以下边界不影响已验证结论的成立，但决定了这套工具当前适用的场景。 它们同时也是使用者判断"这个结果能不能用"的依据。

  • 主尺度统计比例为标定值。 L/B、B/T、L/D 三个比例取自《船舶设计原理》双壳散货船统计带内的合理值； Watson & Gilfillan (1977) 已注册为可选算法，其系数按宪法要求必须以原文为准填入， 不得凭记忆写入。这意味着主尺度反推的 −2.7 % 量级误差是可解释且可改进的。
  • 重量系数为母型船标定。 钢料立方模数、舾装面积模数与机电占比按 TB-001 母型拆分标定， 并显式声明其循环性；零循环验证由教材算例承担。
  • 解析拟合母型仅作交叉校验。 其水线族假设几何相似、球鼻艏外伸未建模、Cw 是拟合产物。 交付链路使用真实数字化型值表；该拟合母型保留在测试套件中。
  • 承载剖面采用线性插值。 数字化网格是 21 等距站，而出版表按 20 站加半站给出， 艉部横梁剖面在水线间非线性，线性插值会低估其积分。 该影响体现在装载锚的 −0.0017 棱形系数偏差内，在 ±0.005 的接受带中。
  • 干舷校核偏保守。 按平甲板、标准舷弧、不做规则减免计算， 且 Cb(0.85D) 以设计吃水的 Cb 替代（水线表只到设计吃水）。 国内法规版本因长度上限 230 m 够不到基准船，不在本版本范围内。
  • 完整验收在散货船船型上完成。 主验收船为 JBC（Capesize 散货船），Series 60 母型承担型线变换与光顺检查的验证。 其他船型在经验公式适用域内的使用，需自行核对边界守卫的返回结果。

复现与参与

10.1 三步复现

# 1. 环境（uv 管理，Python ≥ 3.11）
git clone https://github.com/5777-wq/OpenHull.git
cd OpenHull && uv sync

# 2. 跑一遍完整测试套件（176 条，含全部基准锚点断言）
uv run pytest

# 3. 一条命令跑通设计链路
uv run openhull run examples/taskbook_bulk_carrier.yaml

CLI 只向标准输出流式写结果、不自行落盘——--csv 重定向得到 带 BOM 的表格（Excel 可直接打开，GBK 管道不会崩）， --json 得到完整可序列化结果。同一份任务书两次运行结果逐位相同。

10.2 什么样的贡献最有价值

文献与公式源

项目最大的瓶颈不是编码能力，而是公式原文的获取与核对。 Watson & Gilfillan (1977)、Holtrop & Mennen (1982) 原文、 B 系列螺旋桨回归多项式系数表，都是当前明确挂账的缺口。

独立交叉验证

用一个完全独立的实现（异构语言、异构算法）复算本项目的输出， 是最有价值的贡献形式。项目已把第三方交叉验证列为挂账项。

新的基准船与工况

更多带公开数据的船型（不同船种、不同尺度）能同时检验算法与适用边界， 也是 v1.0 发布门槛的直接支撑。

缺陷与反例

最受欢迎的是能复现的反例：一个超出适用边界却没有报错的输入， 一个应该被光顺检查抓到却没抓到的型值表，一处声明与实现不符。

10.3 项目宪法与协作规范

仓库根目录的 AGENTS.md（中文版 AGENTS_zh.md） 是项目的宪章：单位制与符号表、验证基准与容差总表、公式白名单、 适用边界守卫、禁区清单、代码规范与仓库纪律，共九节。 它同时约束人类与 AI 贡献者——任何与之冲突的代码、测试或文档， 按定义就是错的。修改该文件需要项目所有者明确批准并记录在案。
